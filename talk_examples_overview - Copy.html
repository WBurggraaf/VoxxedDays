How To Read This Report

Every example is grouped under its GitHub repository so a first-time reader can immediately see what project it comes from. Inline code comments also include an aggregate view over 100,000 calls or iterations where that makes the leak easier to understand.

  • Strong provenance: file, upstream discussion, and fix trail line up clearly.

    PR / Discussion Summary

    The PR is about adding a hard nesting limit to XML parsing so the library stops spending unbounded CPU on deeply nested input. The issue matters because the failure mode is not just correctness. One unusually deep document can keep a worker busy long enough for unrelated requests to queue behind it. The maintainers fix that by making the parser fail fast once depth exceeds a configured bound. That changes the resource story from open-ended worst-case work to bounded, predictable behavior.

    Explainer

    The recursive structure made this predictable before the PR existed. Each deeper level means another parse descent, more branches, more object work, and more stack growth, with no explicit budget in the original flow. In a theoretical model, that is exactly how worst-case instruction burn emerges from otherwise ordinary parser code. A likely trace would look like span=xml.parse depth=540 cpu=99% p99=2.8s blocked_downstream=12. The important clue is not just high CPU, but the fact that downstream work starts waiting while one request monopolizes the worker. The before-to-after estimate of `20% to 60%` on extreme inputs, with near-total removal of pathological waste, is therefore reasonable. The PR discussion simply confirms what the code shape and trace prediction already suggested: the parser needed a hard stop. This is a strong example for the talk because it shows that some of the highest-value savings come from bounding work rather than merely speeding it up.

    Prediction Signal

    Before signal: recursive descent with no hard depth stop. After direction: explicit fail-fast bound. Predicted trace outcome: span=xml.parse depth=540 cpu=99% p99=2.8s blocked_downstream=12.
